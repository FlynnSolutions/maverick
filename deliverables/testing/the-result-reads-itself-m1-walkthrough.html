Known going in

The RIOs passed all three tasks (m1-t2 by your call over a mixed verdict) and left these open. They are not cases; note them if you hit them.

old brackets
This mission's own RIOs were briefed before the new line existed, and wrote NOTE: [src/missions.ts, ship] .... Those read as area general with the bracket left in the headline, which is what you will see in v1. Only a RIO briefed from this branch on writes the shape.
rebuilt key
A finding read from a handed-back file is keyed on BLOCKER: plus its text, not on the line as written. Stable, but a mark made on it is orphaned once the task is retried and passes with its own carried lines.
changing a mark
later then read leaves the checklist line and writes no ledger line. If that checklist line was ticked or edited, a second later appends another one.
bad input
A missing state, an unknown state or key, or another task's key answers HTTP 500 with a plain message, as the neighbouring routes do, not 400.
unverified text
On the result page (and in the morning report) a shaped unverified line now files under unverified but keeps its UNVERIFIED(area, check): prefix in the text. Cosmetic; milestone 2 redraws that part.

A task you accepted over the RIO shows none of its findings: your call

decideThe m1-t3 RIO found this, and it is live on this mission. The view reads a task's findings file only while the task is handed-back; accepting it sets passed and carries nothing, so the task where you overrode a blocker is the one the Result section will show empty. It matches the task's words, so it is a spec gap, and m2 draws the section on it. Pass means leave it; fail means fix it before m2 lands (the RIO's cheap fix: also read the file for a passed task whose verdict is fail or mixed and that carries nothing, or have accepting carry the open lines).
