## The model, already decided

Three levels of agent, separated by **blast radius**, not seniority (`docs/03-decisions.md` M5):

- **Air Boss** — holds a whole project, answers questions, writes plan documents, **never edits
  product code**. Not this session's job.
- **Mission**, run by a **RIO** — plans milestones, dispatches workers, validates. **This is what
  you are building.**
- **Wingman** — one item, fresh context, a worktree, a diff. What Maverick already spawns.

The vocabulary is in `docs/07-glossary.md` and it is load-bearing. Don't invent a second set of
words for the same things.

## What I want

One orchestrator that runs a whole piece of work end to end, with me in the loop exactly twice:
once to agree the plan, once to review the result.

1. **It talks to me first.** I describe what I want; it asks clarifying questions and probes
   constraints. It does **not** start on one prompt. This is where most of the value is, so make
   the interview real, not a formality.
2. **It produces a plan**: features grouped into milestones, with what "done" means for each.
   I approve it once. Nothing spawns before I do.
3. **It spins up parallel Wingmen** — one per task, each with fresh context, working
   independently.
4. **Something else reviews them for correctness.** Not the Wingman that wrote the code, and not
   the RIO either. Review runs until the work passes or it is handed back to me. This is the
   part I care most about being right.
5. **The RIO merges** the passing work and brings it back to me as a **session review** I can
   read and actually test.
6. **That feeds the next ship.** The ship wizard already exists; the mission's output should drop
   into it rather than living in a parallel universe.

## The seams that already exist — build on these, don't start fresh

This is most of the reason this is tractable. Read each before designing anything:

- **`src/ships.ts` is the orchestrator skeleton already.** A `ShipRun` is a saved, resumable set
  of `ShipStep`s for one version; each step is a background Claude session with status, a report
  and artifacts, persisted at `~/.claude/console-sessions/ships/<project>/<version>.json`. The
  only reason it isn't a mission is that its steps are parsed from a fixed `SHIP_WORKFLOW.md`
  instead of generated by a planning interview. **A mission is that shape with a generated plan.**
- **`src/formations.ts` is the flight model.** A `Formation` is one `lead` plus `members[]`, with
  REST at `/api/formations` and a UI already built (tabs in the page head, `web/command.js`). A
  mission's RIO is a lead and its Wingmen are the flight. Don't build a second grouping concept.
- **`src/audits.ts` is the validator half, and it is the right shape.** It runs the project's
  `auditor` agent against a finished child session in a background session, the auditor writes a
  findings file whose first line is a verdict, and **the auditor never fixes anything**. That
  separation is deliberate: keep it. What's missing is the loop — audit, hand back, re-verify.
- **The spawn primitive** is `claude --bg --name <name> --permission-mode auto <prompt>`, with
  `--agent <name>` to pick an agent. See `src/ships.ts:153` and `src/audits.ts:96`. The
  background id is parsed out of stdout. `backgroundAgents()` in `src/git.ts` polls
  `claude agents --json --all --cwd <path>` for their state.

## Hard constraints

- **The markdown trackers are the source of truth and Maverick owns no store** (M1). A mission's
  plan is work, so it belongs in the tracker, not in a private database. Work out how a mission
  and its milestones express themselves as tracker items; that design question is part of this
  job, and getting it wrong by adding a store is the main way to get this wrong.
- **No dependencies, no build step** (M2).
- **Nothing machine-specific in source**; everything resolves through `src/config.ts`.
- **Preserve the UI language.** Strips, lamps, reticles, racks, formations, callsigns. Don't
  start a second visual system for missions.
- **I approve before anything spawns.** A mission that starts work off one prompt is a bug, not
  a shortcut.

## Cost discipline, which is why the gate matters

Factory publishes numbers for the equivalent feature: a median mission runs about 2 hours
against 8 minutes for a normal session, burns roughly **12x the tokens**, and 14% run past 24
hours. That is the entire argument for the approval gate and against missions ever being the
default path. Show me what a mission is about to cost before it runs.

## Verify by looking, not by asserting

`node tools/cdp.mjs <url> --shot out.png` and `--eval file.js` drive headless Chrome over the
DevTools protocol; read `tools/README.md`. Two real defects in this repo were invisible in the
CSS and obvious in a computed style, so measure rather than assert. Give pages 6-9 seconds to
settle. For anything multi-agent, assert against the **server state**, not the DOM.

There is no test suite yet and `package.json` has no `test` script. Node 22 has a built-in
runner (`node --test`) that needs no dependency, so if this work wants tests, that is the way in.
